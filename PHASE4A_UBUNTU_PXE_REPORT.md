### 2.3 DHCP / PXE / iPXE / iSCSI / ZFS source inspection

**DHCP** (`examples/etc/dhcp/dhcpd.conf`, generated by `ExportDHCP()` at
`bin/mkyctl.lua:768`): `authoritative`, `next-server 192.168.0.2`, two ranges,
full iPXE option space (`ipxe-encap-opts code 175`, feature indicators,
`iscsi-initiator-iqn code 203`), per-host MAC → fixed-IP entries, and
vendor-class-identifier-based filename selection.

**iPXE chainloading** (`bin/mkyctl.lua:1772-1806`): client PXE boots → DHCP
assigns IP and filename → iPXE loads via TFTP → iPXE calls
`?getmebootargs=<client-ip>` → server resolves the client by IP and emits an
iPXE script with `set initiator-iqn` and `set root-path iscsi:…` per boot image,
then the configured iPXE body/footer. Unknown client IPs get a `#!ipxe` failure
script and are logged.

**iSCSI** (`mkyboot.cmd.tgt` L362-411, `LunAdd` L1308, `tgtstop` L844): targets
created/deleted/bound via `tgtadm` with validated TIDs and IPs; `LunAdd` waits
for the target then adds each enabled `dyndisk` image as a LUN. `valid.service_name`
and `valid.systemctl_cmd` whitelist the privileged operations.

**ZFS / overlays** (`mkChild` L856): `dyndisk` parents are the master image
(supper) or a per-client ZFS snapshot path; `dynblock` parents are the zvol or a
`@<tmpname>_<vid>` snapshot. Per-client lock files guard concurrent creation.

**Image assignment** (`nbdConnect` L1275): per-client overlay path is
`<imgbackdir>/<path><image_prefix><MAC>` with a validated cache mode; `search_nbd`
allocates a free `/dev/nbdN`.

### 2.4 The `supper` boot branch — investigated, documented, not changed

Phase 3 reported that the supper and non-supper boot branches are byte-for-byte
identical. Investigated:

- `bin/mkyctl.lua:1790-1797` (`supper == "1"`) and `:1798-1806` (`else`) both run
  the identical sequence `monit → tgtstop → nbdFree → zfsmount → mkChild →
  nbdConnect → LunAdd`.
- The supper distinction **is** realised elsewhere: `mkChild` (L869-877) selects
  a different parent path for `supper == "1"` (master image) versus
  `supper == "0"` (ZFS snapshot).

**Conclusion:** the identical boot branches are a code smell (dead conditional),
not a functional bug — supper mode changes *which image* is used, not *how* the
boot sequence runs. **No change made**, per the instruction not to make
speculative changes without a test environment.

### 2.5 Defect found and fixed in Phase 4A

**`ipxe32.efi` is offered by DHCP but never installed.**

- `ExportDHCP()` (`bin/mkyctl.lua:810`) emitted `filename "<fileboot>32.efi"`
  unconditionally for 32-bit UEFI clients.
- `srv/tftp/` ships only `ipxe.efi` and `ipxe.kpxe`. No `ipxe32.efi` exists
  anywhere in the repository (the only `*.efi` under `src/ipxe` is a 1.4 KB
  `Makefile.efi` fragment, not a binary).
- The vendored iPXE source **is** present (`src/ipxe/src/Makefile`, arch dirs
  including `i386`), so the binary is buildable on a Linux host with gcc — but no
  compiler is available here.

**Determination: real deployment defect.** The branch is reachable and the file
it names is never installed.

**Fix:** `ExportDHCP()` now offers the 32-bit UEFI filename only when the file
exists in the TFTP root (`mkyboot.cfg.tftp.workdir`, default `/srv/tftp`),
falling back to the 64-bit image with an explanatory comment when it is absent.
The reference is **not** removed — an operator who builds `ipxe32.efi` from
`src/ipxe` still gets the 32-bit path. The TFTP workdir lookup is nil-guarded.
The static example is annotated to match.

## 9. Remaining blockers and exact next actions

1. **Ubuntu runtime validation is the dominant blocker.** Provision an Ubuntu
   20.04/22.04 host or VM with ZFS, then run the §3 command sequence. Until then
   the server is validated by source extraction and stubs only.
2. **`install.sh` was never syntax-checked** (no bash on this host). Run
   `bash -n install.sh` on a Linux host.
3. **Build and install `ipxe32.efi`** if 32-bit UEFI is a supported target:
   `make -C src/ipxe/src bin-i386-efi/ipxe.efi` then copy to `/srv/tftp/`. The
   DHCP config will then offer it automatically. If 32-bit UEFI is **not**
   supported, remove the `elsif` branch from `ExportDHCP()` and the example —
   deliberately, with a comment, not silently.
4. **PXE boot acceptance** requires PXE-capable hardware or a VM. Record DHCP
   lease, TFTP transfer, iPXE script, iSCSI session and OS boot completion.
5. **`go test -race`** requires a C compiler; install MinGW or run on Linux.
6. **Three-copy drift will recur.** A CI check comparing the status and
   server-control regions of the three `mkyctl.lua` copies would prevent it. Not
   added — no CI infrastructure exists in this repo.
